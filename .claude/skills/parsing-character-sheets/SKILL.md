# parsing-character-sheets — текст чарника → gm-character/v1 (локально)

## Overview

Заменяет платную веб-ручку `POST /api/parse-character`: разбор листа персонажа делается
здесь, локально, под подпиской пользователя (Claude Code) — **без ANTHROPIC_API_KEY и без
запущенного go-сервера**. На вход — текст персонажа в любом виде (или приложенный
файл/скрин/PDF). На выход — один валидный JSON объекта `gm-character/v1` в код-блоке,
который пользователь копирует в поле импорта на вкладке «Партия» GM-экрана.

Контракт формата — единый источник истины в репозитории: **`FORMAT.md`** и
**`web/character.schema.json`**. Скилл не изобретает форму заново — он читает контракт и
следует ему буквально.

## Activation Triggers

- «распарси чарник», «распарси перса», «сделай карточку персонажа для экрана»
- «приведи к формату gm-character», «gm-character/v1»
- «parse character sheet», «parse this character»
- Пользователь прислал текст/скрин/PDF листа и просит превратить в карточку партии

## Core Principles

1. **Источник истины — файлы репо.** Всегда сверяйся с `FORMAT.md` и
   `web/character.schema.json`; при расхождении правил в этом файле и в репо — прав репо.
2. **Ничего не выдумывать.** Нет данных в исходнике → строки `"—"`, массивы `[]`,
   `spellcasting` → `null`, неугадываемые числа → `0` + короткая пометка в `notes`.
3. **Только JSON на выходе.** Один код-блок ```json … ``` с объектом (или массивом объектов,
   если персонажей несколько). Никаких пояснений внутри блока.
4. **Аддитивно и безопасно.** Импорт на экране добавляет карточку и не трогает уже
   загруженных персонажей — поэтому достаточно выдать корректный объект, не заботясь о слиянии.

## Workflow

### Шаг 1. Получить исходный текст

- Если персонаж — в сообщении текстом, взять его.
- Если приложен **скрин/фото** — прочитать изображение (`Read` показывает картинку) и снять данные.
- Если приложен **PDF** — прочитать через `Read` с `pages` (или скилл `extracting-pdf-text`
  для сканов). D&D Beyond экспорт в PDF/тексте — брать значения как есть.
- Уточнять у пользователя ничего не нужно, если данных достаточно для заполнения обязательных
  полей (`name`, `abilities`). Пробелы закрывать дефолтами из Шага 3, а не вопросами.

### Шаг 2. Свериться с контрактом

Прочитать в корне репозитория:

```
FORMAT.md                    # человекочитаемый контракт + правила парсера
web/character.schema.json    # JSON Schema, additionalProperties:false
```

Ключи полей — строго латиницей как в схеме; значения-подписи по-русски.

### Шаг 3. Собрать объект по правилам

- `schema` = `"gm-character/v1"` (всегда).
- `abilities` — **значения** характеристик (8–20+), все шесть, ключи `str/dex/con/int/wis/cha`.
  `initiative`, `saves`-бонусы, навыки, `hit` — это **модификаторы**, не значения.
- `hit` — число (бонус к попаданию) или `null` для атак без броска; `damage` — `"NdM+K"` или `""`.
- `saves` — массив ключей характеристик, где есть владение спасбросками (`[]` если нет).
- `prof` по уровню, если не указан явно: ур.1–4=2, 5–8=3, 9–12=4, 13–16=5, 17–20=6.
- `hp.current` = `hp.max` и `hp.temp` = 0, если иное не сказано.
- `conditions` — почти всегда `[]` (состояния мастер ставит за столом).
- Никаких лишних ключей — схема запрещает `additionalProperties`.

### Шаг 4. Выдать JSON

Один код-блок, готовый к копированию:

```json
{ "schema": "gm-character/v1", "name": "…", "abilities": { … }, … }
```

Если персонажей несколько — массив `[ {…}, {…} ]` (поле импорта принимает и объект, и массив).
После блока — одна строка: куда вставлять («Вкладка „Партия“ → поле импорта → Импортировать»).

## Quality Checklist

- [ ] `schema` == `"gm-character/v1"`, есть `name` и все шесть `abilities`.
- [ ] Значения характеристик — не модификаторы; `initiative`/`saves`/`hit` — модификаторы.
- [ ] `hp.current`/`temp` заполнены (по умолчанию = `max`/0).
- [ ] Пустые данные закрыты дефолтами (`"—"` / `[]` / `null` / `0`+notes), ничего не выдумано.
- [ ] Нет ключей вне схемы (`additionalProperties:false`).
- [ ] Вывод — ровно один ```json``` блок (объект или массив), без текста внутри.

## Anti-Patterns to Avoid

❌ **Don't:**
- Дёргать `POST /api/parse-character` или требовать ANTHROPIC_API_KEY — смысл скилла в том,
  чтобы обойтись без платной ручки и без сервера.
- Выдумывать недостающие значения (заклинания, навыки, снаряжение), которых нет в исходнике.
- Добавлять ключи вне схемы или менять латинские ключи полей на русские.
- Заворачивать JSON в пояснения внутри код-блока.

✅ **Do:**
- Читать `FORMAT.md`/`web/character.schema.json` перед сборкой объекта.
- Закрывать пробелы дефолтами (`"—"`/`[]`/`null`/`0`+notes).
- Выдавать один чистый ```json``` блок, готовый к вставке.
- Для нескольких персонажей — массив объектов.

## Summary

Локальный, бесплатный (под подпиской) парсер листа персонажа в `gm-character/v1`. Читает
контракт из репо, заполняет дефолты, отдаёт готовый JSON для аддитивной вставки в GM-экран.
Ноль API-ключей, ноль веб-ручек, ноль риска слить кредиты.
